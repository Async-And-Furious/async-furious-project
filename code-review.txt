## CODE REVIEW - feat/start...feat/EntityOrcamento

---

### 1. VISÃO GERAL DA PR

A branch adiciona a entidade Orcamento ao módulo ordem-servico, implementando funcionalidades
completas de geração, aprovação e rejeição de orçamentos. A mudança engloba:

- Novas entidades e Value Objects: Orcamento, OrcamentoVo (com precisão decimal)
- 3 Use Cases de negócio: Gerar, Aprovar, Rejeitar orçamentos
- Camada de infraestrutura: Repositório Orcamento com Prisma
- Presentation layer: DTOs e endpoints REST com autenticação
- Testes unitários: 400+ linhas cobrindo Value Object e Use Cases
- Schema Prisma: Modelo relacional com relationship 1:1 com ServiceOrder
- Configuração: Integração no módulo com useFactory para injeção de dependência

---

### 2. QUALIDADE E CONSISTÊNCIA DO CÓDIGO

Pontos Positivos:
- Nomenclatura clara: valor_total_servicos, valor_total_pecas, valor_total_geral
- TypeScript adequado: Uso de tipos discriminados ('PENDING' | 'APPROVED' | 'REJECTED')
- Conversão de tipos precisa: toNumber() no VO para evitar problemas com Decimal
- Padrão Clean Architecture consistente: Segue exatamente o mesmo padrão do módulo cadastro

Problemas:
- src/modules/ordem-servico/presentation/dto/ordem-servico.dto.ts:48-56
  @IsNumber({ maxDecimalPlaces: 2 }) não valida precisão efetivamente em class-validator.
  Deveria usar @Min(0) sem maxDecimalPlaces ou implementar validador customizado.
  Risco: Valores como 123.456 passam na validação DTO mas falham no banco.

- src/modules/ordem-servico/infrastructure/repositories/orcamento.repository.ts:20
  Cast "as unknown as Orcamento" é um code smell. Melhor: criar mapper explícito.

- Falta de constantes de erro: Strings hardcoded em múltiplos places.
  A mensagem "Ordem de Serviço com ID ${id} não encontrada" aparece 6x.

### 3. ARQUITETURA E ADERÊNCIA AO CLEAN ARCHITECTURE / DDD

Aderência Geral: 8/10

Respeitado corretamente:
- Separação clara em camadas (domain → application → infrastructure → presentation)
- Use Cases como classes puras sem @Injectable(), registrados via useFactory
- Value Object imutável com validações no construtor privado
- Repository pattern com interfaces bem definidas
- DTOs segregados da camada de domínio

Divergências arquiteturais:
- src/modules/ordem-servico/application/use-cases/orcamento.use-cases.ts:8-10
  Use Cases recebem dois repositórios (IOrdemServicoRepository + IOrcamentoRepository).
  Violação parcial do princípio Single Responsibility.
  Comparar com cliente.use-cases.ts (módulo cadastro) onde cada UC tem 1 repositório.

- src/modules/ordem-servico/domain/interfaces/orcamento.interface.ts
  Interface IOrcamentoRepository não tem método delete() ou remove().
  Inconsistência com IOrdemServicoRepository que tem remove(id).
